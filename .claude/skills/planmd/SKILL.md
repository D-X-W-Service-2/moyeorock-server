# 계획 문서(planmd) 작성 워크플로우

개발에 들어가기 전, 무엇을 어떻게 만들지 정리한 **구현 계획 문서**를 `docs/plans/` 아래 md 파일로 뽑는다.

> **발동 조건**: 사용자가 명시적으로 `/planmd`로 호출했을 때만 이 워크플로우를 수행한다. 일반 개발 요청에서 임의로 발동하지 않는다.
> **범위**: 이 스킬은 **계획 문서만** 작성한다. 실제 구현 코드는 작성하지 않으며, 코드 작성은 사용자가 별도로 요청할 때 진행한다.
> **참고**: `docs/plans/`는 `.gitignore` 대상이다(로컬 전용 작업 문서). git 저장소에는 올라가지 않는다.

## Step 1 — 대상 작업 파악

무엇에 대한 계획인지 확정한다.

- `/planmd` 뒤에 작업 설명이 주어졌으면 그것을 대상으로 한다.
- 설명이 없거나 모호하면 무엇을 계획할지 사용자에게 먼저 묻는다. (CLAUDE.md 작업 방식 — "명세에 없거나 비어 있는 항목은 추측하지 말고 요청한다")

## Step 2 — 관련 컨벤션·코드 파악

계획이 프로젝트 구조·컨벤션과 어긋나지 않도록 근거를 확보한다.

- `CLAUDE.md`의 "작업 전 읽을 문서" 표를 읽고, 작업 유형에 맞는 컨벤션 문서만 선택적으로 읽는다. (`/convention` 스킬과 동일한 방식)
- 필요하면 관련 도메인·기존 코드를 탐색해 영향 범위와 재사용 지점을 파악한다.
- 애매한 설계 결정(어느 도메인/레이어에 둘지, 새 패턴 도입 여부, 스키마 변경 등)이 있으면 임의로 정하지 말고 계획 문서의 "결정 필요 사항"에 남기거나 사용자에게 묻는다. 특히 스키마 변경은 CLAUDE.md 절대 규칙 5(`docs/conventions/erd.md`의 변경 프로세스)를 따른다.

## Step 3 — 계획 문서 작성

`docs/plans/{작업내용}.md` 경로로 파일을 생성한다.

- 파일명: 영문 소문자·하이픈(`-`)만 사용. 관련 이슈번호가 있으면 `#{이슈번호}-{작업내용}.md` 형식으로, 없으면 `{작업내용}.md`로 한다. (`docs/conventions/git-convention.md`의 브랜치 네이밍과 정렬)
- `docs/plans/` 디렉터리가 없으면 생성한다.

아래 골격을 채운다. 해당 없는 섹션은 비우지 말고 삭제한다.

```markdown
# {작업 제목}

> 관련 이슈: #{번호} (있으면)
> 작성일: {YYYY-MM-DD}

## 배경 / 목표

무엇을, 왜 만드는가. 완료 기준(무엇이 되면 끝인가)을 한두 줄로.

## 범위

- 이번 작업에 포함되는 것
- 포함되지 않는 것 (명시적으로 제외)

## 영향 범위 / 관련 도메인

- 건드리는 도메인·레이어와 그 이유 (`docs/conventions/architecture.md` 호출 방향 준수 여부 포함)
- 참고·재사용할 기존 코드

## 구현 계획

작업을 커밋 단위로 나눠 순서대로 나열한다. (`docs/conventions/git-convention.md` — 작업 단위별 커밋 분리)

1. [ ] {단계 — 무엇을 어디에}
2. [ ] {단계}

## DB / 마이그레이션 (해당 시)

- 추가·변경할 테이블·컬럼·인덱스, `docs/conventions/erd.md` 변경 계획, 필요한 Flyway 파일(`docs/conventions/flyway-migration.md`)

## 결정 필요 사항 / 리스크

- 아직 확정 못 한 설계 선택지, 사용자에게 확인이 필요한 부분
- 예상되는 위험·주의점
```

## Step 4 — 결과 안내

- 생성한 파일 경로를 알린다.
- "결정 필요 사항"에 남긴 항목이 있으면 그 부분을 사용자에게 짚어주고, 확정 후 구현에 들어갈 것을 안내한다.
- 이 스킬은 여기까지다. 구현 착수는 사용자의 별도 지시를 기다린다.
